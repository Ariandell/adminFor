# Налаштування Supabase

Адмінка використовує чинні таблиці `courses`, `lessons`, `cards`, `tags`, `card_tags` і розширює їх новими полями та сутностями з ТЗ.

1. Відкрийте Supabase Dashboard → SQL Editor.
2. Виконайте файл `supabase/migrations/202608160001_content_admin.sql`.
3. У Table Editor перевірте, що з’явилися таблиці `homework`, `achievements`, `cosmetics`, `subscription_plans`, `promo_codes`, `marketing_sources`.
4. Для конструктора досягнень послідовно виконайте `supabase/migrations/202609010001_achievement_rules.sql` і `supabase/migrations/202609010002_achievement_contexts.sql`.
5. Для конструктора підписок виконайте `supabase/migrations/202610220001_subscription_builder.sql` після базової міграції.
6. Перед production-запуском замініть тимчасові permissive RLS-політики `admin_all` на політики для авторизованої ролі адміністратора.

Після міграції в адмінці працюватимуть рівні карток, неправильні дієслова, основні/додаткові курси, premium-замки, домашні завдання, досягнення, косметика, тарифи, промокоди та джерела реклами.

## Конструктор підписок

`202610220001_subscription_builder.sql` розширює чинну таблицю `subscription_plans`: додає опис, HTTPS-зображення, `updated_at` і версійовані налаштування `entitlements`. Код тарифу може бути довільним унікальним значенням із 2–64 малих латинських літер, цифр, `_` та `-`; перший символ — літера або цифра. Старі чотири коди залишаються чинними. Періоди `month`/`year`, рівні `basic`/`premium` та всі старі записи зберігаються.

Контракт налаштувань:

```json
{
  "version": 1,
  "features": {
    "translation": { "enabled": true, "limit": 50, "period": "day" },
    "personal_cards": { "enabled": true, "limit": 100, "period": "total" },
    "course_dictionary": { "enabled": true, "limit": null, "period": null }
  },
  "courses": { "mode": "selected", "ids": ["a1111111-1111-4111-8111-111111111111"] }
}
```

- Денний ліміт доступний для `translation`, `speaking_review`, `pronunciation_review`, `flashcards`, `ai_assistant`. `personal_cards` обмежує загальну кількість власних карток.
- `course_dictionary`, `irregular_verbs`, `word_statistics` — лише доступ без числової квоти. Наявність параметра в тарифі не означає, що заплановану функцію вже реалізовано в додатку.
- `ai_text_review`, `advanced_statistics`, `premium_cosmetics` прибрано з конструктора, підсумків і нових конфігурацій. Старі записи з цими ключами залишаються читабельними; після редагування вони більше не записуються. SQL-контракт допускає відсутні відомі ключі як вимкнені, тому додаткова міграція не потрібна.
- Числова квота — ціле значення від 1 до 1 000 000. `enabled: true` з обома значеннями `limit`/`period`, рівними `null`, означає доступ без тарифної квоти. Вимкнена функція має `enabled: false`, `limit: null`, `period: null`.
- Бонусна валюта `reward_currency` — ціле значення від 0 до 1 000 000; негативні та завеликі бонуси відхиляються також у базі.
- Курси: `none` — не включені, `all` — усі, `selected` — конкретні UUID. Для `selected` потрібні 1–1000 різних ID; для `none`/`all` список порожній. Саме налаштування не публікує чернетки курсів.
- В адмінці: «Підписки» → створити або редагувати → «Доступ до курсів» → «Пакет вибраних курсів». Позначте потрібні курси галочками: у кожного тарифу власний набір, назви видно в попередньому перегляді та списку підписок. Нові курси не потрапляють у такий пакет автоматично; режим «Усі опубліковані курси, зокрема майбутні» включає їх після публікації.
- Невідомі ключі/версії відхиляються; відсутні відомі ключі означають вимкнений доступ. Старі `features` та `ai_requests_limit` не перетворюються автоматично, бо їхні попередні значення не визначали точні права й періоди. `entitlements = NULL` означає старий неналаштований тариф.

Міграцію можна виконати повторно. Вона не додає тарифів, не змінює ціни, покупки, підписки користувачів, RLS або права ролей. Нові перевірки полів додано як `NOT VALID`: історичні записи не переписуються; нові й змінені рядки обов'язково проходять перевірку. Після ручної перевірки старих даних можна окремо валідувати `subscription_plans_builder_fields_check` та `subscription_plans_entitlements_check`.

Для перевірки SQL-контракту є `supabase/tests/subscription_builder.sql`: валідні/невалідні квоти, точні ключі, режими курсів, дублікати UUID, ціна, URL та сумісність старих тарифів. Скрипт використовує тимчасову таблицю й завершується `ROLLBACK`; не створює справжніх тарифів.
